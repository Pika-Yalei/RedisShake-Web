## 2. 项目现状

- Go 后端、原生 JavaScript 前端、SQLite 存储、RedisShake 固定内核补丁、Docker Compose 和四平台构建脚本已实现；验证范围见 [验证记录](verification.md)。
- 已确认面向个人或小团队自部署，核心模式为全量迁移后持续同步增量。
- 对标已定位到 RedisSyncer，已核查公开文档中的任务管理流程，见 [参考分析](benchmark-redissyncer.md)。
- 已确认 Docker 和本机直接运行两种部署方式，Linux、macOS 直接运行与 Docker 都支持 x86_64/ARM64；最低系统版本尚需工程设计固定。
- 已确认保留单管理员账号密码登录，不做多账号、角色和权限管理。
- 已确认支持单机、哨兵和 Redis Cluster，九类源端到目标端组合纳入设计，见 [支持矩阵](support-matrix.md)。
- Redis 大版本范围为 6.x、7.x、8.x，第一版只支持自建 Redis；同版本、升级和降级方向均纳入设计验证。
- 高级规则全部纳入；已有数据策略提供要求目标为空和覆盖同名 Key，默认要求目标为空。
- 不兼容时报错停止，DB 映射先做一对一；长期运行已纳入核心范围。
- 长期同步失败后由用户确认重新全量，内核优先官方版本，必要时允许少量补丁。
- 第一版单向 A → B，目标端业务写入不回传；双向及防循环留待后续。
- 两端业务写入由应用侧管理，产品按内核正常写入，不实现冲突检测、仲裁或合并。
- 已确认独立连接管理与连接复用，不提供内置数据核验。
- 经用户授权拟定初始基线：当前固定最多 5 个并发任务、单任务 10 GiB、连续运行 24 小时验收；后两项尚未实测。
- 任务操作已确认；提供目标 DB 清理按钮并二次确认，不做自动清理或外部通知。
- Redis 仅明文；前端使用原生 HTML/CSS/JavaScript 和项目自有组件；后端继续按 Go + SQLite 规划。
- Linux、macOS 运行包和 Docker 镜像均覆盖 x86_64、ARM64。
- 多 Key 部分匹配时整条跳过并记录原因；中文界面，原始日志保留原文。
- 已确认只做增量命令过滤，不做数据类型过滤；DB/Key 规则仍作用于全量和增量。
- 首次在 Web 设置管理员账号和密码；本机解压后执行一个命令启动。
- Web 重启不打断同步，采用常驻执行器持续管理内核，恢复后的 Web 重连；进程与故障边界见 [运行设计](runtime-design.md)。
- 执行器直接连接 Redis；统一性能参数，不提供页面性能选项；采用三项导航与四步创建向导。
- 哨兵源端选择与复制流中的整库清空命令待第十五轮确认，其余工程默认值集中整理。
- 当前处于实现与冒烟验证阶段，完整支持声明要等矩阵和容量验收完成。

## 3. RedisShake 调研与约束

资料核查日期：2026-09-23。以下是上游公开说明，不等于本产品已承诺支持全部上游能力。

| 上游事实 | 对产品计划的影响 |
| --- | --- |
| 官方展示以配置文件启动 RedisShake 的使用方式。 | 可评估由后端生成配置并管理独立进程；具体集成方式尚待验证。 |
| 上游提供 PSync、RDB、Scan 等读取方式。 | 本版按已选场景使用 PSync 全量加增量；不增加 RDB 文件导入或 Scan 模式选择。 |

| 官方说明不支持集群拓扑变化感知。 | 集群支持范围、迁移中故障切换、扩缩容的处理方式必须验证并写入产品行为。 |

已固定 RedisShake v4.6.2 并校验源码归档，内核入口与内部包已直接合入本项目 Go 模块；每个迁移任务由主程序内部 `task` 模式运行在独立进程中。本项目对内核的修改和当前实测结果见 [验证记录](verification.md)。版本/拓扑冒烟不等于容量、稳定性或全命令兼容性验收。

### 对标借鉴范围

RedisSyncer 文档的基本任务流程为创建、启动、查看状态、停止和删除，借鉴该任务管理方式。其 Dashboard 为单独发布的 Web 控制面板；本产品已确认三项导航与四步创建向导，视觉由实现方设计，不承诺复刻参考 UI；尚未实测参考项目的 UI。

来源与具体建议见 [RedisSyncer 参考分析](benchmark-redissyncer.md)。参考产品的内核能力不直接转为 RedisShake Web 的功能承诺。

## 4. 用户主流程

主导航和创建向导已确认，详细字段与异常行为见 [交互规格](product-spec.md)。

1. 首次打开 Web 设置唯一管理员账号和密码；以后输入账号密码登录。登录成功进入迁移任务列表，空列表显示创建入口。
2. 创建或选择源 Redis 连接，填写必需连接信息并测试连通性。
3. 创建或选择目标 Redis 连接，测试连通性。
4. 配置 DB 选择与一对一映射、Key 前缀/正则、增量命令过滤；默认要求目标为空，也可明确选择覆盖同名 Key。不提供数据类型筛选。
5. 执行预检查，展示通过项、阻断项和需要用户确认的影响。
6. 查看迁移摘要，点击启动；后端创建一次独立运行记录并调用 RedisShake。
7. 在详情页查看真实阶段、可取得的进度、日志和错误；无法计算的指标明确显示不可用。
8. 全量完成后进入长期增量同步，不设置自动结束时间；持续展示运行事实与错误。
9. 用户需要完成业务切换时，自行核验数据并操作业务切换，再按约定停止同步。第一版不提供内置数据比对或验证报告。失败时展示原因与下一步，不把已有目标写入视为已回滚。

所有步骤仍需补齐：页面入口、字段及校验规则、默认值、按钮可用条件、加载与空状态、错误反馈、退出与返回、重复点击、浏览器刷新后的行为。

### 已确认的部署与访问范围

- 必须交付服务器 Docker 运行方式和本机直接运行方式。
- 两种方式都通过浏览器操作，业务功能和任务数据语义保持一致。
- 第一版不提供用户新增、成员管理、角色配置和细粒度权限管理。
- 保留单管理员账号密码登录；首次直接在 Web 初始化账号和密码，已登录后的密码修改与会话采用 [运行设计](runtime-design.md) 中的工程默认方案。
- 直接运行覆盖 Linux、macOS；Windows 直接运行未纳入本次第一版选择。
- x86_64 与 ARM64 均支持；本机解压后执行一个启动命令，最低系统版本由固定依赖与构建验证确定。

以下为已确认体验对应的工程方案，详细设计见运行设计文档：

- 一个发布包提供 Web 页面、管理服务和匹配平台的 RedisShake 内核，避免普通用户另行编译内核。
- Docker 镜像与直接运行包使用相同的配置规则、任务状态机和内核版本。
- 持久化目录存放连接、任务、运行记录及按约定保留的日志；Docker 使用数据卷，本机运行使用明确的数据目录。
- 浏览器关闭及 Web 服务重启不停止任务。常驻执行器独立管理内核、写入状态和日志；Web 重连恢复控制，不重复启动内核。
- Docker 采用 Web、执行器两个服务以支持独立重启 Web；重启整个部署、执行器容器或整机不承诺继续同步，需人工重新全量。
- 已确认只采用直接网络连接，不引入 SSH 隧道、远程执行节点或分布式调度。

### 数据规则的设计要求

已确认：第一版需要 DB 选择与映射、Key 前缀/正则包含或排除，以及仅作用于增量阶段的命令过滤，不需要数据类型过滤。已有数据策略提供“要求目标为空”和“覆盖同名 Key”，默认前者。

实现计划需要明确并验证：

- DB 筛选依据源端 DB，一对一映射到目标 DB，不允许多个源 DB 合并；迁到集群时仅选择一个源 DB 映射到 DB 0。集群目标限制需在表单及预检中表达。
- Key 前缀和正则作用于哪个阶段，包含与排除冲突时的优先级。
- 多 Key 命令只部分匹配时整条跳过并记录原因，不拆分命令；预览与表单说明必须表达该行为。
- 命令包含/排除列表只作用于复制流解析出的增量命令；全量导入生成的 RESTORE、SET、HSET 等不受这些列表影响。
- 不提供按 Key 实际类型、命令组或数据类型变化跟踪的筛选入口；命令名称采用选定内核的命令定义。
- 所有阶段先按源端 DB/Key 筛选，再对增量条目应用命令规则，最后做 DB 映射并写入。排除优先，允许列表为空表示该类别默认放行。
- 空目标检查的范围、检查时间及启动前并发写入的处理；覆盖同名 Key 的策略与增量语义。

内核证据：官方过滤器在转换前执行，排除规则优先，多 Key 命令要求全部 Key 通过，否则整条丢弃；正则采用 Go 语法。官方 Lua 钩子可以调整目标 DB。[过滤器文档](https://tair-opensource.github.io/RedisShake/en/filter/filter.html)、[转换钩子文档](https://tair-opensource.github.io/RedisShake/en/filter/function.html)

阶段区分需要先行验证：当前公开 v4 的 `Entry` 没有全量/增量来源字段，主循环统一调用过滤器，不能直接把全局 `allow_command`/`block_command` 当成“仅增量”规则。[Entry 源码](https://github.com/tair-opensource/RedisShake/blob/v4/internal/entry/entry.go)、[主循环源码](https://github.com/tair-opensource/RedisShake/blob/v4/cmd/redis-shake/main.go)

拟采用小补丁：由读取组件为每条数据携带明确来源阶段，增量命令过滤仅检查增量条目；DB/Key 筛选和 DB 映射保持两阶段生效。必须按条目标记，不能用一个全局“已进入增量”变量或日志时间判断，因为集群各节点可能处于不同阶段。固定版本后复核该方案。

采用四步向导的可视化表单生成规则及 DB 映射，无需用户编写 Lua。Web 的预览、后端校验与内核执行必须保持相同语义。

### 跨版本迁移与可行性验证

- 已确认 Redis 6/7/8 的同版本、升级、降级方向全部纳入范围，见 [版本矩阵](support-matrix.md)。
- 不能将“内核可连接这个版本”直接视为“任意数据都能无损迁到其他版本”。
- 官方提供通过 RESP 命令重建数据来规避部分降级时的 RDB 编码差异，但目标缺少的数据类型与命令仍需单独处理。[跨版本迁移文档](https://tair-opensource.github.io/RedisShake/en/others/version.html)
- 必须验证降级重建路径与“覆盖同名 Key”策略是否兼容，特别是 List、Hash、Set、ZSet 等结构重跑后不能意外追加或保留旧成员。
- 必须验证降级重建、原生 RESTORE 和增量路径的阶段标签正确，防止增量命令规则误伤全量导入。
- 已确认不兼容时报错停止，不自动跳过。预检能发现时阻止启动，运行中才出现时记录错误并停止任务；停止不等于回滚此前已写入的数据。
- 全量预检不能保证预知未来新增的增量命令，仍需要运行时错误处理。不能提前宣布所有组合已经可实现或已验证。

### 长期运行与恢复设计

长期同步已列为核心需求，需在实现普通页面前确定恢复方案。详见 [长期同步设计议题](long-running-sync.md)。

- 已选人工恢复：故障报错停止，用户确认并处理目标范围后发起一次新的全量运行；不自动拉起失败任务。
- 优先官方发行版，必要时允许少量补丁；补丁需记录原因、上游版本、验证结果及升级维护方式。
- 已确认两端可以有业务写入，产品仍只按单向 A → B 正常同步，不增加应用冲突管理；重建规则需遵守该边界。
- 计划必须包含资源上限、日志轮转、运行事实核对、失联反馈、故障处理和长时间稳定性验证。
- 重新全量的目标数据处理必须单独设计，不能把覆盖已有 Key 当作完整恢复方案。

### 两端业务写入的已确认边界

- 只实现 A → B，B 的业务写入不回传 A；双向与防循环属于后续范围。
- 不要求产品检测两端业务是否写同一 Key，不增加哪一端优先、时间戳比较或自动合并机制。
- 按 RedisShake 正常写入：保留已确认的全量目标策略，增量按过滤、映射后的命令写入。
- “正常写入”不等同于按业务发生时间决定最新值，也不承诺有目标端独立写入时两端始终相等。
- 第一版不提供内置数据核验，不显示“数据一致”或类似未经验证的结论；应用侧自行决定业务切换条件。
- 用户可通过独立按钮清空所选目标 DB，执行前二次确认；正常启动、失败和重新全量操作都不自动清空。

### 任务操作与目标清理

- 已确认任务操作：草稿、编辑未运行任务、启动、停止、重新全量、复制任务、删除已停止任务。
- 不提供暂停续传、自动重试或定时启动；后两项没有纳入当前已选操作范围。
- 清理仅操作用户明确选择的目标 DB 中的全部 Key，不受任务 Key 过滤规则限制；确认页面必须展示该范围。
- 不使用 RedisShake 的 `advanced.empty_db_before_sync` 实现清理：当前 v4 主程序该选项执行 FLUSHALL，范围与“清空所选目标 DB”不同。生成配置必须保持其关闭，清理由执行器独立实现并测试。[上游主程序](https://github.com/tair-opensource/RedisShake/blob/v4/cmd/redis-shake/main.go)
- Cluster 目标仅有 DB 0，清理需覆盖目标集群的各主节点，并明确显示“整个目标集群”，不能只清理入口节点后报告完成。
- 清理与本工具在同一目标范围执行的任务互斥，服务端再次检查；不接管外部应用的写入。
- 清理部分成功或拓扑变化时，展示逐节点结果并报告未完成，不自动重试或自动开始同步。
- 只在清理命令结果已确认后显示完成；清理完成不保证外部业务不会立即写入新 Key，启动仍需重新执行空目标检查。
- 第一版失败只在页面与日志展示，不接入 Webhook、邮件或聊天通知。

清理命令依据：[Redis FLUSHDB 文档](https://redis.io/docs/latest/commands/flushdb/)。该命令删除当前 DB 的 Key，不删除 Redis Functions；Cluster 只有 DB 0。集群逐节点执行与结果汇总属于本产品需要实现的逻辑。

### 连接管理与状态展示

- 独立连接管理页面支持保存 Redis 连接，并在创建任务时选择源连接、目标连接。
- 连接表单按单机、哨兵、集群切换字段，并提供测试连接；支持无认证、密码、ACL 用户名/密码，第一版不提供 Redis TLS。连接编辑/删除细节见交互规格草案。
- 每次运行保存实际使用的配置快照；建议编辑共享连接不直接修改正在运行的内核配置，新运行再使用更新后的配置。
- 第一版展示任务状态、全量/增量阶段、运行时间、错误与日志。可取的运行指标后续按真实接口设计，不承诺无法可靠取得的进度百分比。
- 不提供抽样或全量数据比对、TTL 核验、差异修复和数据一致性报告。

### 初始规模与工程验收基线

用户授权由实现方确定，当前采用以下基线；这是开发与验收目标，尚未实测：

- 当前同时运行上限固定为 5 个任务；达到上限时拒绝新启动并说明原因，不排队。可配置上限留待容量验收后评估。
- 容量验收覆盖单任务 10 GiB 的源端逻辑数据；是否允许更大任务不通过该数字硬编码限制。
- 稳定性验收连续运行 24 小时，覆盖持续新增、更新、删除与过期，不仅是空闲进程存活。
- 参考执行机采用 8 vCPU、16 GiB 内存及 200 GiB SSD 可用空间；源/目标 Redis 独立提供资源。实际测试必须记录运行环境。
- 分层执行小数据功能测试、单任务容量测试、5 任务并发测试和长时间运行测试，避免用一个测试结果替代所有维度。
- 不预先承诺固定吞吐或全量耗时；记录测试负载、数据类型、网络、吞吐、积压变化和资源占用后形成发布说明。
- 工程验收需要检查数据内容与 TTL，以验证实现正确性；这些测试能力不作为产品内置功能发布。

## 6. 系统职责与进程边界

后端继续采用当前方案 Go + SQLite，RedisShake 以独立进程运行；用户已明确将前端改为无框架的原生 JavaScript。具体页面行为正在整理为 [交互规格](product-spec.md)。

| 模块 | 建议职责 | 需要解决的关键问题 |
| --- | --- | --- |
| Web 界面 | 数据连接、创建向导、预检反馈、任务列表与详情。 | 普通用户完成迁移所需的最少配置。 |
| Web 管理后端 | 提供页面与 HTTP 接口，将认证、查询、控制请求交给执行器。 | 会话校验、输入反馈、浏览器刷新与 Web 重启后的重连。 |
| RedisShake 适配层 | 生成配置、启动和停止内核、记录版本、解释运行结果。 | 内核接口边界、错误映射、真实指标来源。 |
| 常驻执行器 | 独立持有 SQLite、凭据、进程生命周期、运行目录、日志和并发控制。 | Web 退出后持续运行；控制请求幂等；执行器故障后的运行核对。 |
| 预检组件 | 检查连接、版本、拓扑与迁移前提。 | 不将连接成功或内核运行状态表述为数据一致性验证通过。 |

Web 与常驻执行器必须分进程，以满足 R-039；其他组件作为 Go 内部模块。同机进程通过本地 Unix socket 通信，执行器是数据写入和任务控制的唯一入口；不让两个进程分别决定是否启动同一任务。详细生命周期、首次初始化和部署边界见 [运行设计](runtime-design.md)。已确认不提供远程 Agent。

## 7. 实施阶段及退出条件

### P0：完成需求澄清

- 每轮集中确认 1～3 个相关问题，将答案记录为决策。
- 先确定对标流程、目标用户与迁移目标，再深入页面、数据语义、异常和工程约束。
- 输出最终范围、非目标、支持矩阵、页面交互和验收标准。
- 退出条件：没有影响实现的未决关键问题；保留的非关键假设已明确标注。

### P1：验证内核集成

- 固定 RedisShake 版本与制品来源。
- 在隔离测试数据上验证确认范围内的迁移模式。
- 验证配置生成、退出码、信号处理、日志和指标。
- 验证停止、故障、重新运行及目标端冲突行为。
- 验证只重启 Web 时 RedisShake 进程及复制会话持续运行、日志不中断、重连不重复启动；分别注入执行器崩溃、容器重启和整机重启以验证故障边界。
- 验证哨兵发现与源端节点选择、集群节点可达性、跨拓扑迁移限制；接入拓扑和迁移中自动恢复分别验收。
- 验证高级规则在全量与增量中的实际行为，尤其是恢复命令、多 Key 命令、删除、过期和类型变化。
- 将降级迁移、覆盖已有复合结构、仅增量命令过滤组合设为早期技术验证重点；如现有内核无法满足，先记录证据和必要改动，再更新实现设计。
- 第一版没有 Redis TLS，证书上传及 TLS 补丁不进入实现任务。调研发现当前 v4 分支 `getTlsConfig` 跳过证书校验，作为未来引入 TLS 时需重新核查的记录保留。[当前上游客户端源码](https://github.com/tair-opensource/RedisShake/blob/v4/internal/client/redis.go)
- 对选定的长期运行恢复方案做先行验证；若要求超出原版内核能力，将扩展工作单列并先验证可行性。
- 验证目标端业务写入存在时仍按约定单向重放，状态与错误不误导为具有冲突协调能力。
- 输出能力矩阵和可复现的集成验证记录。
- 退出条件：产品承诺能对应真实能力；不支持的行为已调整设计或明确排除。

### P2：确定工程设计

- 确定技术栈、目录结构、持久化方式、接口契约。
- 明确连接、任务、运行记录和事件的数据模型。
- 明确状态转换条件、操作幂等、并发控制和服务重启后的核对机制。
- 明确凭据存储和日志脱敏方式。
- 输出按依赖排序的实现任务，每项关联需求编号和验收条件。
- 退出条件：实现者不需要自行补充关键产品规则。

### P3：打通第一条真实迁移流程

- 实现建立连接、预检、创建任务、启动内核、查看运行状态及结果。
- 优先验证用户确认的首要迁移组合。
- 使用真实 Redis 与 RedisShake 验证前后端完整链路。
- 退出条件：从 Web 完成该场景，不需要用户手写配置或运行内核命令。

### P4：完成确认范围内的功能和异常处理

- 扩展支持矩阵内的其他迁移组合和配置。
- 完成运行记录、日志、停止和重试等已确认功能。
- 完成失败反馈、刷新恢复、多次提交、服务重启等明确要求。
- 退出条件：所有需求都有实现及验证结果，不以模拟进度代替真实运行结果。

### P5：验收和交付

- 执行真实迁移集成测试、关键界面操作验收和故障场景验证。
- 验证打包安装、首次启动、配置持久化及必要的升级流程。
- 分别验收 Docker 与本机直接运行，并覆盖最终确认的操作系统和处理器架构。
- 执行约定时长的持续同步及故障注入验证，检查资源增长、日志保留、恢复结果和数据差异。
- 提供用户指南、部署指南、支持矩阵和已知限制。
- 退出条件：确认范围内的验收项全部通过；遗留问题有明确处置结论。

## 8. 最终验收框架

下列复选框表示完整发布验收，不因小数据量冒烟通过就自动勾选。已实现与已实测的具体范围见 [验证记录](verification.md)。

- [ ] 用户通过 Web 完成所选迁移场景，无需编辑 RedisShake 配置。
- [ ] 页面显示的迁移阶段和结果与内核运行事实一致。
- [ ] 全量完成、增量运行、主动停止和失败有清晰区分，不显示未经执行的数据核验结论。
- [ ] 源/目标组合、数据类型、TTL 和过滤行为按支持矩阵完成验证。
- [ ] 停止、失败重试及服务重启的行为符合约定，不误导用户为断点续传。
- [ ] 目标端数据冲突和重复执行遵守约定策略。
- [ ] 连接凭据不出现在普通日志、错误提示或非必要接口响应中。
- [ ] 页面刷新及重复点击不会产生未授权的重复运行。
- [ ] 在约定的部署方式和运行平台上可重复安装并完成迁移。
- [ ] Docker 和本机直接运行均可通过浏览器完成相同的核心迁移流程。
- [ ] 第一版不依赖多账号、角色或权限配置才能完成迁移。
- [ ] 管理员登录后可以管理全部连接与任务，未登录不能调用受保护的管理接口。
- [ ] 支持矩阵内的九类拓扑组合有验证结果；限制能在配置、预检或运行错误中明确反馈。
- [ ] Redis 6/7/8 全部版本方向按兼容规则验收，不能仅通过放开版本校验来宣称支持降级。
- [ ] 两种目标数据策略符合配置说明；高级规则在全量、增量与降级路径上有对应验证。
- [ ] 不兼容数据或命令导致明确失败，不静默跳过，也不显示为迁移完成。
- [ ] DB 映射保持一对一，目标 DB 冲突与集群目标限制在启动前拦截。
- [ ] 长期运行在约定负载与时长下通过稳定性和故障场景验证，恢复方式与真实能力一致。
- [ ] 断网或内核退出后展示失败，保留运行记录，不自动重新全量；新的运行由用户明确触发。
- [ ] 单向 A → B 按正常写入语义验收；不回传 B 的业务写入，不宣称提供冲突仲裁或双向一致性。
- [ ] 重新全量不会擅自清理目标端其他业务数据。
- [ ] 清空目标 DB 需独立操作和二次确认；Cluster 清理结果覆盖全部目标主节点，部分失败不会显示整体成功。
- [ ] 已保存连接可供多个任务复用，连接变更与运行配置之间的关系符合约定。
- [ ] 通过单任务 10 GiB、5 任务并发与连续运行 24 小时的分层验收，并记录环境和资源占用。
- [ ] 前端不引入 UI 框架或 TypeScript，共用表单、弹窗、表格、状态和日志组件由原生 JavaScript 实现。
