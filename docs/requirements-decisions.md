### Q-033：类型过滤的准确语义

换一种表述继续询问：第一版是否直接使用 RedisShake 已有的筛选能力，选择允许或排除哪些命令类别，界面写清含义；暂不额外实现“只迁移某种数据类型，并跟踪该类型 Key 的所有变化”？

- 不，需要“只迁移 Hash 等指定类型的数据”这种严格筛选。

用户最终补充：「按照增量命令过滤就行了，不需要按照类型过滤」。

状态：已确认，见 D-037。保留 DB/Key 筛选和 DB 映射，不提供类型或命令组筛选；命令包含/排除仅作用于增量。当前上游统一过滤路径需要在固定版本上验证并按已授权范围补齐阶段区分。

## 后续澄清顺序

根据前一轮答案调整后续问题，每轮优先解决最影响方案的 1～3 项。

1. 部署和访问：运行位置、网络、用户数、登录及角色。
2. 迁移边界：版本与拓扑、云服务、TLS/ACL、模式与文件导入。
3. 数据规则：DB 与 Key 范围、冲突处理、TTL、过滤与映射。
4. 关键交互：页面布局、创建向导、预检、启动、状态与结果。
5. 运行与异常：并发、停止、重试、服务重启、拓扑变化、日志。
6. 验收标准：数据验证、切换流程、规模与性能、部署交付。
7. 工程方案：技术栈、持久化、内核适配、接口与任务拆分。

## 实施前必须消除的歧义

- 第一版明确包含什么、不包含什么。
- 每个用户操作触发什么行为、何时成功、何时被阻止。
- 每种迁移模式的完成条件与失败处理。
- Web 展示的数据来自哪里，无法可靠取得时如何反馈。
- 服务端和迁移进程异常后如何核对事实，避免错误显示或重复启动。
- 谁根据什么证据确认迁移可用于业务切换。

满足这些条件后，将计划更新为可执行基线；不提前将当前草案标记为需求已全部确认。
