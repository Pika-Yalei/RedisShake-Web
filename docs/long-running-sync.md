# 长期同步设计议题

更新日期：2026-09-23  
状态：长期单向同步、人工重新全量恢复和允许少量内核补丁已确认；不介入应用写入冲突，不内置数据核验；重新全量操作仍待细化。

## 已确认要求

- 一次全量迁移后持续同步增量，用户要求长期运行。
- 不兼容数据或命令报错停止，不允许静默跳过。
- 第一版 DB 映射只做一对一，不合并多个源 DB。
- 支持自建 Redis 6/7/8、单机、哨兵和集群；覆盖不同版本方向。
- 目标端要求为空或覆盖同名 Key 两种策略，默认要求为空。
- 故障时报错停止，由用户确认后发起新的全量运行，不自动恢复或重试。
- 优先官方 RedisShake，必要时允许维护少量补丁。
- 两端均可有业务写入，产品只做 A → B；不检测、仲裁或合并应用写入冲突。
- 双向同步及防循环留在后续范围。
- 第一版仅展示同步状态与日志，不内置数据核验。
- 失败通知仅在页面与日志中呈现，不接入外部渠道。
- 提供清空所选目标 DB 的独立按钮，执行前二次确认，启动或重新全量不自动清空。
- 经用户授权拟定默认 5 任务并发、单任务 10 GiB 与 24 小时持续运行的分层验收基线。

长期运行不设置自动结束时间；需要切换业务时仍由用户执行。自动恢复不在第一版范围内；重新全量的目标处理、恢复耗时和目标可用性需细化。

## 已核实的内核边界

RedisShake 4.x 官方不支持断点续传和集群拓扑变化感知。断网、进程崩溃、服务重启、集群扩缩容或故障切换可能中断同步，重新启动需要重新全量同步。官方将高可用长期同步列为不适用场景。

来源：[RedisShake Checkpoint 文档](https://tair-opensource.github.io/RedisShake/en/others/checkpoint.html)，核查于 2026-09-23。

因此，本产品将长期运行定义为持续执行与观测，并在失败后由用户触发重新全量。不能将后端拉起进程等同于恢复同步，也不能把第一版标记为高可用同步系统。

## 恢复方案决策

| 方案 | 用户可见行为 | 需要解决的问题 |
| --- | --- | --- |
| 故障停止，人工重新全量（已选） | 任务显示失败、原因和受影响阶段；用户按约定处理目标数据后明确发起新的运行。 | 重新运行入口、目标处理、历史记录、失败告知方式。 |
| 自动重试，允许重新全量（第一版不做） | 此前讨论的候选方案。 | 无需纳入第一版实现任务。 |
| 断点续传（第一版不做） | 此前讨论的候选方案。 | 无需纳入第一版实现任务。 |

选择记录见 D-021；尚未实施。任何后续范围变更都需同步修改状态机、界面文案与验证计划。

## 全量重建必须解决的数据语义

这是工程分析，需要实测验证，不是上游已提供的能力承诺。

- “允许覆盖已有 Key”不能独立解决重新全量的一致性：例如断线期间源端删除了一个 Key，目标端可能仍保留它，重新导入源端剩余 Key 不会自然清除该残留。
- 已确定由用户独立触发所选目标 DB 的全部 Key 清理并二次确认，不受任务 Key 过滤规则限制；需要展示影响范围并与本工具活跃任务互斥。
- 删除目标数据、覆盖数据、停止同步和删除任务记录必须在界面中分别表达。
- 复合结构重新导入要验证不会重复追加或留下旧成员，尤其是降级时转换为命令的路径。
- 全量重建过程中目标端是否允许读取、读取结果可能处于什么状态，需要形成使用约定。
- 不兼容导致的失败与暂时断网不同，不能不加区分地自动重试。

## 两端业务写入

用户已明确：第一版只做单向 A → B；应用侧写入不由本产品管理，按 RedisShake 正常写入即可。

- 保留全量阶段已选择的目标数据策略；增量按过滤和映射后的命令正常写入。
- 不检测或强制划分两端业务写入范围，不做冲突优先级、时间戳仲裁或自动合并。
- B 的业务写入不回传 A，双向及防循环留到后续。
- 第一版不内置数据核验，也不自动修复目标数据；业务切换前的数据检查由用户自行负责。
- 清理目标是独立操作，用户选择目标 DB 并二次确认后执行，不由失败重试或启动流程自动触发。外部应用写入不由本工具冻结。

工程分析：重放源端命令会作用于目标当时的数据，可能覆盖、计算或删除目标现有内容。因此正常写入不提供两端应用写入冲突的协调保证。

## 长期运行需要补充的设计

1. **任务生命周期**：用户停止、内核失败、服务重启、人工重新全量和完成业务切换的状态分别定义；失败任务不会自动重试。
2. **服务与执行进程关系**：已确定 Web 与常驻执行器分离，浏览器关闭和 Web 重启不停止同步。执行器、其容器及整机重启按故障停止、人工重新全量处理，详见 [运行设计](runtime-design.md)。
3. **运行事实核对**：避免残留进程、重复拉起、重复写入和任务实际停止但界面仍显示正常。
4. **资源控制**：任务并发、CPU/内存、缓存与日志空间、背压及磁盘不足的处理。
5. **监控**：运行阶段、吞吐、积压、最近成功写入或指标采样时间，明确空闲与采集失联的区别。
6. **日志与历史**：轮转、大小上限、保留策略、错误摘要及故障追踪。
7. **配置变更**：运行时是否允许修改连接和过滤规则，修改后是继续、重启还是重新全量。
8. **正确性验证**：产品不内置数据核验；开发与发布验收仍使用受控测试数据验证同步内容、过滤结果、映射和 TTL。
9. **运维**：页面失败状态与日志、升级停止窗口、备份恢复和人工处置步骤；第一版无外部告警。
10. **拓扑变化**：哨兵切主、集群故障切换与扩缩容分别定义支持及恢复边界。

## 必须完成的验证

- 在持续新增、更新、删除、过期的数据负载下进行约定时长的稳定性验证。
- 分别注入源端断线、目标端断线、内核退出、管理服务重启、容器/整机重启。
- 覆盖写入已发生但确认丢失的故障窗口，验证不会将不确定结果标为完整成功。
- 验证哨兵切主、集群节点失效与槽位变化的真实行为。
- 验证过滤、DB 映射、降级和覆盖策略在恢复路径上仍满足约定。
- 验证长时间空闲、持续高写入、积压增长、日志轮转和磁盘不足。
- 验证多任务同时失败或人工重新运行时不会超出并发和资源约束。

初始验收基线已定：单任务 10 GiB、5 任务并发、连续运行 24 小时分层验证；参考执行机为 8 vCPU、16 GiB 内存、200 GiB SSD 可用空间，Redis 另供资源。基线是目标，尚未实测，不预先保证吞吐。
